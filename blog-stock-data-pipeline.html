1. Introduction & Motivation1. บทนำและแรงบันดาลใจ

For those following my journey: I'm currently studying data engineering, an area I'm excited to grow into. After finishing a course, I decided to build a portfolio project to turn theory into practice and strengthen my understanding. I explored many sample projects and found one that covers the tools and concepts I want to learn — so I started building it end-to-end.

Before I begin, a quick thank-you to Jay for his clear "building a portfolio" tutorial — it made getting started much easier.

Let's begin! The main idea behind this project is to build a dashboard with two key pages:

  • YTD Performance Dashboard — to track year-to-date stock performance at a glance.
  • Intraday Trading Dashboard — to monitor live market movements throughout the day.

To make both dashboards work, I needed data sources that could provide both real-time and historical stock data. After exploring a few options, I decided to use Finnhub.io API for real-time market data and Yahoo Finance for reliable historical data. These two sources together gave me everything I needed to start building a complete end-to-end project.

2. Data Pipeline Architecture2. สถาปัตยกรรม Data Pipeline

After deciding on my data sources, the next step was to design the data pipeline. Here's how my setup works:

For the first data source — the real-time stock data — I pull data from the Finnhub.io API and send it to Kafka, which acts as the message broker to handle and store the incoming data stream.

At this point, I paused for a moment and asked myself:

"Why do I need Kafka here? Why not just send the data directly to MinIO for storage?"

Curious, I did a bit of research — and here's what I found:

  • With Kafka: The pipeline becomes more resilient, scalable, and flexible. It's the industry standard for building real-time data systems that can handle failures and high throughput.
  • Without Kafka: The setup is simpler, but also more fragile. There's no buffering, so a failure could break the data flow, and it's much harder to scale later on.

Understanding this trade-off made it clear why Kafka is often used as a middle layer — it's not just about storing data, but about making the pipeline future-proof.

That's also the reason why my second data source — the historical data from Yahoo Finance — doesn't go through Kafka. Instead, it sends data directly to MinIO. The main reason is that historical data doesn't need second-by-second updates. Its granularity is daily, so if the pipeline or API fails, I can simply rerun the job and still retrieve accurate data.

Pipeline Design

For this part, I designed two pipelines:

  • Year-to-Date Pipeline: Runs once to fetch all data from January 1, 2025 up to the current date when the pipeline is executed.
  • Daily Update Pipeline: Runs regularly to fetch the most recent day's data (yesterday's prices) and merge it with the existing year-to-date dataset.

Once both setups are in place, the system runs smoothly — the dashboards automatically receive real-time data from Finnhub and daily historical updates from Yahoo Finance. Together, they ensure the data behind both dashboards stays fresh and complete without any manual intervention.

MinIO Data Organization

In my MinIO bucket, the data is organized into three folders:

  • ytd_historical_data
  • real_time_data
  • daily_historical_data

Once all the data successfully lands in MinIO (our data lake), the next step is to load it into Snowflake, which serves as the data warehouse.

4. Building the Kafka Producer4. สร้าง Kafka Producer

That's all for the design part — now let's dive into the coding. I started with the producer script, which is responsible for fetching data from Finnhub.io and sending it to Kafka.

The basic idea is simple: the producer pulls data every 5 seconds and streams it to Kafka.

But then I paused for a moment and thought — what happens if the script runs 24/7, even when the market is closed?

If we keep hitting the API every few seconds during non-trading hours, we'd be wasting API calls and consuming unnecessary resources. Since Finnhub's API has request limits, I needed a smarter approach — one that keeps the pipeline active only during market hours.

Smart Polling Strategy

So, I came up with a simple concept for the polling condition:

First, set the local date and time to align with the U.S. market timezone.

ET = pytz.timezone('US/Eastern')

Then, define the polling strategy so that the producer will run based on below condition.

# MARKET HOURS (EASTERN TIME)
MARKET_OPEN = dt_time(9, 30)
MARKET_CLOSE = dt_time(16, 0)
MARKET_DAYS = [0, 1, 2, 3, 4]  # Mon-Fri

def is_market_open() -> bool:
    """Check if US stock market is currently open (using Eastern Time)."""
    now_et = datetime.now(ET)

    # Check if weekend
    if now_et.weekday() not in MARKET_DAYS:
        return False

    # Check if within market hours
    current_time = now_et.time()
    return MARKET_OPEN <= current_time <= MARKET_CLOSE

# POLLING STRATEGY
class PollingStrategy:
    MARKET_OPEN: int = 5       # Every 5 seconds during market
    MARKET_CLOSED: int = 300   # Every 5 minutes after hours
    WEEKEND: int = 3600        # Every 1 hour on weekends
    BEFORE_MARKET: int = 60    # Every 1 minute before market opens

    @staticmethod
    def get_interval() -> int:
        """Get appropriate polling interval based on Eastern Time."""
        now_et = datetime.now(ET)
        current_time = now_et.time()
        day_of_week = now_et.weekday()

        # Check if weekday (Mon-Fri)
        if day_of_week in MARKET_DAYS:
            # Before market opens
            if current_time < dt_time(9, 30):
                return PollingStrategy.BEFORE_MARKET
            # During market hours
            elif dt_time(9, 30) <= current_time <= dt_time(16, 0):
                return PollingStrategy.MARKET_OPEN
            # After market closes
            else:
                return PollingStrategy.MARKET_CLOSED

        # Weekend
        return PollingStrategy.WEEKEND

Producer → (push) → Kafka Broker → (pull) → Consumer → (save) → MinIO

Monitoring & Alerts

At this stage, I noticed an opportunity to improve the system's monitoring and reliability. Right now, there's no alert mechanism to track whether the producer or consumer fails. If something goes wrong, I wouldn't know until I manually check the logs.

To fix this, I came up with a solution: create a small Python heartbeat script that monitors both the producer and consumer. If either of them fails, the script would send a message to Slack, notifying me whether the pipeline is running smoothly or needs attention.

Later, I also integrated this idea into the Airflow DAG that transfers data from MinIO to Snowflake — which I'll explain in the next section.

6. Orchestration with Airflow6. Orchestration ด้วย Airflow

Now comes the orchestration part — where Airflow truly takes the stage.

To make this easier to follow, I'll break down my Airflow script into sections — each one starting with the problem I faced and the solution I used to build the bronze_stock_quotes_raw table, which stores all the incoming real-time stock data.

Step 1: Setting Up Slack Alerts

The first issue I ran into was error visibility. If the DAG failed, I wouldn't know right away. So, I decided to integrate Slack alerts using a webhook, allowing Airflow to send me real-time notifications whenever something went wrong.

Before adding this to the script, you'll need a Slack Webhook URL. (In my setup, I stored it as an Airflow Variable, along with the credentials for MinIO and Snowflake — so you won't see them directly in the code.)

Here's how you can create your own Slack webhook step by step:

  • Go to https://api.slack.com/apps
  • Click "Create New App" → "From Scratch"
  • Give it a name, for example: "DataPipeline Alerts"
  • Enable Incoming Webhooks
  • Click "Add Webhook to Workspace" → choose your alert channel (e.g., #data-alerts)
  • Copy the Webhook URL
  • Add the webhook to your Airflow Variables

Step 2: Configuration and Health Check

Before loading any data, it's important to make sure all the connections — especially to MinIO and Snowflake — are properly configured.

To keep things clean and reusable, I decided to store all my credentials inside Airflow Connections instead of hard-coding them. If you want to use the same setup as mine, here's how I configured it:

  • MinIO connection name: minio_s3
  • Snowflake connection name: snowflake_default

Once the configurations were set, I added a quick health check step to the DAG. This step tests whether the connections to MinIO, Snowflake, and the Consumer script are all working correctly.

Step 3: The Efficiency Challenge

When I first built the pipeline, I didn't think much about efficiency. Everything worked fine — until I hit a wall.

One day, I had to upload around 60,000 files from MinIO to Snowflake. The process took forever. My original script was performing a deduplication check for every single file: it downloaded all the data, compared each record against what was already in Snowflake (using (symbol, timestamp) as a unique key), and only uploaded new entries.

It worked, but it was painfully slow. The pipeline was supposed to deliver real-time insights — not spend ages checking for duplicates. This step became a serious bottleneck, especially since I needed to refresh data every 5 minutes.

To fix this, I flipped the logic. Instead of downloading everything first, I made the script query Snowflake upfront to identify what data already existed. Then, it only downloaded and uploaded the new records that hadn't been stored yet.

This small change made a huge difference — the pipeline now runs much faster and more efficiently, allowing real-time data updates to flow smoothly without delays.

Step 4: Main ETL Process

Here's how it works: first, the script checks which data already exists in the database. Then, it scans all files in storage and skips those that have been previously loaded. Only new files are downloaded to the local machine and uploaded to Snowflake using 20 parallel workers — like having 20 people working at once instead of just one — to speed up the process.

After that, all data is copied into the database table in a single batch, temporary files are cleaned up, and a notification is sent once everything is complete. The entire process is designed to run automatically and safely, ensuring no duplicate records are created, even if the pipeline runs multiple times.

Step 5: Task Dependencies

The dependencies are quite straightforward. After verifying all connections, Airflow automatically downloads files from MinIO, loads them into Snowflake, and logs every step of the process.

If something goes wrong — whether it's a connection issue, missing file, or data mismatch — the error is recorded in the audit table, making it easier to trace and debug later.

7. Transformations with dbt7. Transformations ด้วย dbt

Before we begin, make sure dbt is installed in your project environment.

Setting Up Snowflake Tables

I forgot to mention earlier that my minio_to_snowflake script doesn't include a function to create or replace tables in Snowflake. So before running the script, please ensure the target table already exists in your Snowflake database.

Here's what you need to do once you're in Snowflake:

USE ROLE ACCOUNTADMIN;
USE DATABASE STOCKS_MDS;
USE SCHEMA COMMON;
DROP TABLE IF EXISTS bronze_stock_quotes_raw;

CREATE TABLE bronze_stock_quotes_raw (
    -- Raw data columns
    close_price DECIMAL(10, 2),
    price_change DECIMAL(10, 2),
    price_change_percent DECIMAL(10, 4),
    high_price DECIMAL(10, 2),
    low_price DECIMAL(10, 2),
    open_price DECIMAL(10, 2),
    prev_close DECIMAL(10, 2),
    symbol VARCHAR(10),

    -- Timestamps
    quote_timestamp TIMESTAMP_NTZ,
    fetched_at TIMESTAMP_NTZ,

    -- Metadata
    raw_json VARIANT,
    load_timestamp TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),

    -- Constraints
    CONSTRAINT pk_stock_quotes PRIMARY KEY (symbol, quote_timestamp)
);

After creating the table, switch to the DATA_PIPELINE_ROLE, which will handle all the Airflow processes. Finally, grant the necessary permissions to this role so it can access and manage the table properly.

GRANT USAGE ON DATABASE STOCKS_MDS TO ROLE DATA_PIPELINE_ROLE;
GRANT USAGE ON SCHEMA STOCKS_MDS.COMMON TO ROLE DATA_PIPELINE_ROLE;
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA STOCKS_MDS.COMMON TO ROLE DATA_PIPELINE_ROLE;
GRANT ALL PRIVILEGES ON FUTURE TABLES IN SCHEMA STOCKS_MDS.COMMON TO ROLE DATA_PIPELINE_ROLE;
GRANT CREATE STAGE ON SCHEMA STOCKS_MDS.COMMON TO ROLE DATA_PIPELINE_ROLE;
GRANT ALL PRIVILEGES ON ALL STAGES IN SCHEMA STOCKS_MDS.COMMON TO ROLE DATA_PIPELINE_ROLE;
GRANT USAGE ON WAREHOUSE COMPUTE_WH TO ROLE DATA_PIPELINE_ROLE;
GRANT OPERATE ON WAREHOUSE COMPUTE_WH TO ROLE DATA_PIPELINE_ROLE;

Building the Bronze Layer with dbt

The next step is to build the bronze layer using dbt. This part depends on how you want your final data table to look, so you can create your own SQL model file accordingly. Store the file under the following path in your project: models/bronze/stg_stock_quotes_raw.sql

-- models/bronze/stg_stock_quotes_raw.sql

{{ config(
    materialized='table',
    database='STOCKS_MDS',
    schema='bronze',
    description='Raw stock quote data from MinIO with minimal transformations'
) }}

SELECT
    -- Keys
    symbol,
    quote_timestamp,
    fetched_at,

    -- Price data
    open_price,
    high_price,
    low_price,
    close_price,
    prev_close,

    -- Change metrics
    price_change,
    price_change_percent,

    -- Metadata
    raw_json,
    load_timestamp,
    CURRENT_TIMESTAMP() as dbt_loaded_at,

    -- Add row number for deduplication in silver
    ROW_NUMBER() OVER (
        PARTITION BY symbol, quote_timestamp
        ORDER BY load_timestamp DESC
    ) as rn

FROM {{ source('stocks', 'BRONZE_STOCK_QUOTES_RAW') }}

WHERE
    -- Filter out null symbols
    symbol IS NOT NULL
    AND close_price IS NOT NULL
    AND quote_timestamp IS NOT NULL

Integrating dbt with Airflow

At this point, I started questioning myself again — do I really need to integrate dbt with Airflow to ensure my tables always have the latest data as soon as it's loaded into Snowflake?

Doing so would make my setup more complex, since I'd need to run dbt inside Docker rather than outside as before. But for the sake of automation and scalability, I decided to take that challenge.

The first step was to create a Dockerfile.dbt and then include dbt in the docker-compose.yml configuration.

FROM python:3.11-slim

# Install system dependencies
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
    git \
    && apt-get clean \
    && rm -rf /var/lib/apt/lists/*

# Install dbt with SNOWFLAKE adapter
RUN pip install --no-cache-dir \
    dbt-core==1.7.4 \
    dbt-snowflake==1.7.3 \
    protobuf==4.25.3

# Set working directory
WORKDIR /dbt

# Set environment variables
ENV DBT_PROFILES_DIR=/dbt

# Keep container running
CMD ["tail", "-f", "/dev/null"]

After that, I added dbt into the Airflow script. The logic was simple: once the data finishes loading into Snowflake, dbt should automatically run to update the tables. This way, the dashboard always grabs the latest, most accurate data for visualization.

Enabling Docker API

To make that happen, there were two main steps:

  • Apply the dbt command to the Airflow script
  • Enable Docker API access

Here's how to enable the Docker API in Docker Desktop:

  • Open Docker Desktop
  • Click the Settings (⚙️) icon
  • Go to General
  • Check "Expose daemon on tcp://localhost:2375 without TLS"
  • Click Apply & Restart

Finally, I added one more step — the dbt_test job. This step helps prevent any null or missing values from being loaded into the table. If dbt detects an error during this test, I manually review and update the missing data before the next run.

8. Power BI Visualization8. Visualization ด้วย Power BI

Let's wrap things up with the final step — visualization.

Open a new blank Power BI file, then click on "Transform Data" and select Snowflake as your data source.

A credential window will pop up where you'll need to enter your connection details. The Server field refers to the server path shown in your Snowflake session details, and the Warehouse is your compute resource — in my case, it's called 'COMPUTE_WH'.

Once connected, you'll see all the available tables from your Snowflake environment. And that's it — your data integration is complete! From here, it's all about creativity — how you want to tell the story behind your data through visuals.
